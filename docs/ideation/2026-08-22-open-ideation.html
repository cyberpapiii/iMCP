Grounding Context

iMCP is a macOS menu-bar app that owns TCC and service toggles, plus a bundled imcp-server stdio proxy. The CLI prefers loopback via an owner-only listener-endpoint file (port + pid, signed-process check), then Bonjour. Pairing is a P-256 fingerprint and a one-way signed-nonce AUTH preamble. PairedClient stores only fingerprint, label, and addedAt. Gates are global service enablement plus connection approval. Enabling Messages publishes iMessage to every paired client. ListResources and ListPrompts return empty arrays. Write verbs are asymmetric. Plans 001–035 are done; the Aug 21 review-trust pass closed pairing persist, Team-ID pins, and honest MCP errors, and deferred status, Resources, scopes, and pairing-code transport.

The solutions store holds one convention: AGENTS.md is the only instruction body. Pairing, discovery, and FetchPolicy have no compounded docs. The 2026 field is crowded (MacRelay, AppleMCP, AirMCP, pointer-first macos-apps-mcp). Differentiation is moving to governance, pointer catalogs, and protocol surfaces (Resources, Tasks, MCP Apps) — not another Calendar fetch. Official Apple MCP is Xcode/Safari tooling, not personal data.

1. Grant instrument

Conf 88% Complexity Medium

Pairing answers “who is this binary.” It does not answer “what may this conversation read.” Keep PairedClient as identity. Mint a separate grant — prize list, term, and revocation — at approval or first dangerous write. Start with Messages: a session or a one-client house key, not a menu-bar switch that floods every roommate.

Basis
direct: PairedClient is only fingerprint, label, addedAt. Approval copy says the client can use every enabled service. Messages is one messagesEnabled bit. external: AirMCP sells profiles and HITL into that gap.
Rationale
Without a grant object, every later governance idea (audit, HITL, iPhone confirm) has nowhere to live. With one, they share storage, UI, and tests. Messages is the service people leave off or overshare.
Downsides
Approval becomes a real product moment, not Allow/Deny. Existing paired clients need a migration default (likely “current global enablement, no Messages until re-granted”).

2. Two-world trust

Conf 86% Complexity Medium

Today the bundled CLI already proves the listener via a signed pid in the endpoint file, then still runs the same P-256 AUTH and pairing dialog as a LAN stranger. Split the worlds. Same-user signed imcp-server on loopback is local process identity. AUTH, pairing codes, and Bonjour are the remote product — an explicit “Allow LAN clients” door the GUI can be prompted for. Spawned stdio should fail immediately when the endpoint file is missing, not hang on Bonjour.

Basis
direct: loopback is exempt from Local Network; Bonjour hangs in .preparing when that permission is denied. The endpoint file does not authenticate the process on the named port. reasoned: deleting pairing for every spawned CLI would collapse distinct hosts into one peer — keep pairing for foreign clients.
Rationale
This is the daily hang. Claude’s disclaimer spawn never gets a Local Network prompt. Treating Bonjour as the stdio failure path converts “app is not publishing loopback” into a 15-second shrug.
Downsides
Need a crisp definition of “same-user signed CLI” so a random local process cannot skip pairing. Bonjour stays for a human-attended LAN client, or it is retired on purpose.

3. Reading-room catalog

Conf 84% Complexity High

Do not implement Resources as the same JSON-LD dumps under a new method. Tools return handles (event id, note id, thread id, photo id) plus a caption. ListResources is the catalog. ReadResource is the only body path — metered, logged, optionally redacted. Notes already fetch bodies by id; Messages and events still circulate the manuscript.

Basis
direct: ListResources returns []. external: macos-apps-mcp pointer catalogs; MCP 2026-07-28 Resources. reasoned: a circulating-stack Resource recreates today’s dump. A special-collections rule reduces wire bodies because agents stop calling fetch-everything to discover what exists.
Rationale
Body dumps blow context and overshare. One body door is where redaction, FetchPolicy, and a future journal attach. This is the 2026 differentiator that is not “add a 17th service.”
Downsides
Breaks hosts that assume tool results are complete records. Needs a migration story and a clear handle scheme. High implementation burden across 16 services.

4. Mutual AUTH

Conf 82% Complexity Medium

AUTH v1 is one-way: the CLI signs a nonce and connection id chosen by whoever challenged. Pairing codes still travel as --pair and IMCP_PAIR_CODE. Make the app sign the endpoint advertisement (or a server-auth frame). Keep the issuer in memory; stop putting the whole secret in argv or env — owner-only sidecar or inherited fd. Do not claim the pairing secret can “never be a string.”

Basis
direct: AuthPreamble.protocolVersion = 1; payload is nonce then connectionID. Endpoint-file comments: the CLI signs a challenge from whatever peer answers the port. Pair UI still prints argv and env bearers.
Rationale
Review-trust hardened the file and left the speaker unauthenticated. Mutual AUTH plus a non-ps pairing handoff closes the leftover that every “pair Claude” instruction still teaches.
Downsides
Protocol bump. Debug ad-hoc signing must stay compatible with install-local.sh. Sidecar consume-on-read needs a race story for two spawned clients.

5. Dark-harbor notices

Conf 90% Complexity Low

When loopback fails, the CLI should name the failed check — app quit, stale or unsigned endpoint file, recycled pid, zero services — in loopback-then-Bonjour order. Publish a Light List in the endpoint file (which lights are lit). Advertise liveness as a Resource, not an imcp_status tool. A status tool requires the harbor the ship cannot enter.

Basis
direct: stdio timeout always cites Local Network. Endpoint miss silently returns Bonjour. File contents are port + pid only. Last plan forbade imcp_status as a tool. external: MCP Resources/Tasks are the spec-shaped home for operator state.
Rationale
This is the daily “iMCP is broken” ticket. Until the CLI can name the failed check, new tools and Notes search stay unreachable from the hosts people actually use.
Downsides
Widening the endpoint file is a compatibility change. Do not put secrets or message bodies in the Light List.

6. Intent ledger

Conf 78% Complexity Medium

Create-only Calendar and Reminders train agents to duplicate the user’s life. Contacts can already update. Treat that asymmetry as a decision, not an accident: agents propose writes; the signed app UI (menu bar, later a phone) commits. Expanding full CRUD makes iMCP a generic PIM API in a crowded field. Removing write authority from the pipe is the other pole. The ledger is the middle that stays a local personal-data MCP.

Basis
direct: events_create and reminders_create exist; no update/delete. Approval is connect-time, not write-time. external: AirMCP preview/HITL. reasoned: a create-only verb in a loop-driven agent is a duplication engine.
Rationale
Last plan’s “no CRUD” was a stop condition. This is the product law: iMCP is allowed to draft, not to quietly rewrite identity.
Downsides
Proposal inbox is new UX. Existing Contacts update may need to become a proposal too, or stay the exception with a written reason.
